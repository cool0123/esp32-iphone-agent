# 电脑端控制能力现状（2026-10-31 实测）

## 结论先说

没有 Mac 就无法构建 iOS App；不构建 App，电脑端就**只能“看”，不能可靠“点”**。
下面每条都是实测结果，不是推测。

## 已验证可用

| 能力 | 证据 |
|---|---|
| AirPlay 抓帧 + 硬解 | 常驻 ffmpeg 解码，单帧约 40 KB，实测 3–6 fps |
| 模型读屏判断 | 多次真实任务中正确识别界面并给出行动 |
| BLE 命令通道 | `ping/move/click/stream/snap/ota/resync` 均返回 ok |
| 运行中切换 Wi‑Fi | STA↔AP 三轮往返，`mdr=6 mdf=0`，无重启 |
| 空中升级 OTA | 连续 5 次成功，`rst=software`，版本号可核对 |
| 供电修复 | USB 声明改总线供电 500 mA 后，2 分钟镜像零掉电 |
| 镜像中断保护 | 运行中检测到 `ap != streaming` 立即停止 |

## 已验证不可用（关键阻塞）

### 1. 鼠标绝对定位无法校准

- iOS **不把鼠标指针画进镜像画面**：移动 3 次后 AirPlay 一帧未发；帧差仅剩左上角 8–20 px 的细微变化。
- 因此无法用“移动→找指针”的办法测出比例与偏移。
- 实测误差：命令 (211,741) 实际落在约 (96,820)，即数十像素级偏差，会点到相邻图标。
- 曾出现过的小圆点，事后确认是**悬停高亮**，不是光标。

### 2. 键盘：能打字，但不能导航

可确认的事实：

- `type hello` 确实把文字输入到了备忘录的输入框（用户目视确认）——说明键盘 HID 通。
- "全键盘控制"确认已开。
- 在设置首页实测 `tab` / `down` / `down` / `enter`：画面差异仅 27–43 像素，且全部落在状态栏 x10–34 / y16–23，
  即左上角那块指针残影，**列表没有任何焦点环或选中移动**。

结论：打字可用，**焦点导航不响应**。因此键盘不能替代鼠标做导航。
（若要再试，可换一个「键盘导航」兼容性更好的设备/系统版本；本项目在 iOS 26 上到此为止。）

### 3. 静止画面后无新 IDR

- 一个镜像会话**只在开始时发一个 IDR**，之后全是 P 帧（实测 14 分钟内 `idr_age` 持续增长，无第二个 IDR）。
- 后果：会话开始较久后，新的解码器无法启动；`snap` 需要重发整个 GOP，BLE 传不完。
- 现有对策：
  - 固件 `SNAP_MAX_BYTES = 800 KB`，超限立即返回 `err gop N KB too large`（0.0 秒，不再卡 120 秒）；
  - 固件 `resync` 命令 + 客户端 `--resync`：断开 RTSP 会话，迫使 iOS 重新协商出新 IDR（需要人在手机上点一次「屏幕镜像 → ESP32 Agent」）。
- 因此**每次运行前需要重开一次镜像**，或使用 `--resync`。

## 由此产生的使用限制

- `ds_loop.py` 适合：链路验证、读屏判断、单次点击尝试、OTA、状态巡检。
- `ds_loop.py` 不适合：需要连续准确点击的多步任务（打偏会误开应用或点到「停止镜像」）。
- `precise` 在找不到指针时会**取消点击**，这是有意为之，不要改成盲点。

## 唯一可靠解法

用 iOS App 本体（仓库 `ios/`）。App 在设备内运行，能用**触摸探针**自校准：
自己发触摸 → 自己抓落点 → 拟合直线 → 后续点击按直线修正。
电脑端无法复制这条路，因为电脑看不到指针、也拿不到触摸落点。

构建 App 需要 macOS + Xcode 26（设备是 iOS 26）。用户当前没有可用的 Mac、云 Mac 与 USB 直通，故 App 路径暂时阻塞。

## 仍未解决

- BLE 控制命令未强制加密/绑定（附近设备理论上可发命令）。
- `bo`（掉电计数）在 OTA 传输期间仍会增长。
- 服务端 8787 仅局域网可用，UFW 未放行。
- iOS App 的旧帧保护、远程运维页面尚未真机验收（需 Xcode）。
